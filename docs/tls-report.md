# TLS inspection milestone report - 29 October 2026

Implemented in the existing working tree, preserving prior milestones and unrelated
local work. No commit, push or deployment was performed. The operational details
and reproducible commands are in the [TLS guide](tls-inspection.md).

| Requested report item | Implementation and measured result |
| --- | --- |
| 1. TLS architecture | Dedicated deterministic `services/tls.py` adapter and `tls_live.py` evidence renderer. Two address-pinned handshakes: retrieve the presented leaf, then validate with the local runtime. Cryptography parses certificates; urllib3 provides maintained hostname matching because the old Python ssl helper is unavailable. No LLM determines facts. |
| 2. Inventory integration | Reuses the monitor URL hostname and explicit/default HTTPS port, including internal hostnames and literal IPs. No duplicated target settings. HTTP/no-monitor services are skipped. Batch inspection targets HTTPS only. |
| 3. Certificate fields | Hostname, port, selected address, connection success, certificate presentation, subject, issuer, serial, SHA-256 fingerprint, validity start/expiry, remaining seconds/days, typed SAN entries, hostname result, runtime validation result/code/reason, TLS protocol, cipher tuple, timestamp and total latency. |
| 4. Validity/trust/hostname semantics | Independent fields. Date validity comes from UTC certificate dates and the system clock. Runtime validation uses default trust roots with hostname checking disabled for that handshake; hostname matching runs separately against names/IP SANs. Runtime validation includes chain/date checks. Primary states prioritize expired/future, hostname mismatch, failed trust, unavailable validation, <=30-day warning, then valid; no-data stays unknown. |
| 5. Self-signed handling | A reachable self-signed endpoint has connection success and a presented certificate, with failed runtime validation and its bounded reason. It is not declared down. The unchanged HTTP probe still rejects that certificate unless inventory explicitly configured otherwise beforehand. |
| 6. Safety controls | Same HTTP address policy applied to every resolver result, pinned numeric connection with original SNI, no redirect or HTTP exchange, no credentials or client certificates. Eight-second overall budget; three-second connection/handshake limit; four cross-caller inspection slots; bounded DNS worker reuse, resolver results, leaf DER and SAN data; 50-target batch and five-second cooldown. Inspection sockets are aborted after measurement without waiting for peer shutdown. Nothing alters certificates, trust stores, services or HTTP verification. |
| 7. API changes | POST and GET `/api/services/{id}/tls`; GET returns stored latest/history/change flags. `GET /api/services?health=true` attaches stored TLS summaries. Existing probe concurrency and service lookup controls are reused. No arbitrary-target or certificate-writing endpoint. |
| 8. CLI changes | `grimoire services tls [name-or-id]`, all configured HTTPS targets when omitted, and `--json`. Human output includes state, hostname/port, issuer, expiry/lifetime, hostname match, runtime trust/reason, validity, protocol and observation time. No model load required. |
| 9. UI changes | Services view adds concise TLS state and Inspect TLS action for HTTPS monitors; presentation, expiry/lifetime, hostname result, runtime trust reason, protocol, saved checked time, stale and change labels. Text uses safe DOM text assignment. Eight frontend tests and JavaScript syntax checks pass; no browser screenshot acceptance was performed. |
| 10. Live evidence changes | Distinct `tls_observation`, T label, observation ID, service/hostname, nested full measured certificate/TLS facts and retained samples. Answers cite the TLS label, with readable deterministic summaries. Documentation, DNS and HTTP evidence types stay distinct. Model commentary remains in its separate existing field. |
| 11. History/change detection | Existing SQLite observation architecture, separate TLS table, 50 samples per service and 5,000 globally, transactional pruning, persistence and deletion cleanup. Comparable successive samples detect fingerprint, issuer, SAN, expiry and runtime-trust changes. No comparison across changed targets or absent certificates, and no unsupported renewal or long-term claim. |
| 12. DNS/TLS/HTTP correlation | Failure questions can include all three separately timestamped observation types. Explicit refresh can measure them; ordinary questions read saved results. Certificate-only refresh never sends an HTTP request. Correlation cites individual samples and says they do not establish causation. No automatic certificate-verification bypass was added. The existing DNS correlation regression now uses a deterministic TLS fixture and asserts all three evidence types while preserving DNS/HTTP facts. |
| 13. Real local acceptance | PASS with generated disposable certificates and real loopback sockets: trusted-valid, self-signed/untrusted, trusted-chain hostname mismatch, expired, not-yet-valid, expiring-soon, plaintext and refused connection. Timeout is additionally exercised with a real stalled loopback fixture in automated tests. API/CLI/chat acceptance confirms an untrusted certificate is presented while HTTP remains unreachable due to verification failure. [Saved local evidence](tls-evidence/local.json). Existing inventory contains zero configured HTTPS targets; no real LAN HTTPS service was tested. Test roots exist only in disposable in-memory SSL contexts; no trust store was modified. |
| 14. Automated tests | 33 new TLS backend cases covering dates, SAN parsing, DNS/IP/wildcard matching, self-signed trust, actual handshakes/plaintext/timeouts, DNS/policy failures, malformed/bounded DER, capacity, change detection, retention/reopen/delete/global cap, evidence/question routing, API, CLI and JSON. Final complete backend gate: **487 passed**; frontend: **8 passed** (two new TLS tests). Total **495 passed**, including all prior 37 HTTP monitoring and 28 DNS cases. Ruff, changed Python formatting, JavaScript syntax and diff whitespace checks pass. [Backend XML](tls-evidence/backend-tests.xml). One existing Starlette/httpx deprecation warning remains. |
| 15. Reliability regression | Real local Qwen2.5-1.5B Q4_K_M and MiniLM CPU suites rerun unchanged, command exited 0. Development: supported/oracle 10/10 each; unsupported/oracle 4/4 each; citations 18/18; logs/extraction/incidents 6/6 each; retrieval hit@5 10/10. Held-out: supported/oracle 22/22 each; unsupported/oracle 5/5 each; citations 25/25; logs/extraction/incidents 7/7 each; retrieval hit@5 22/22. [Full evidence](tls-evidence/reliability.json), [summary](tls-evidence/reliability-summary.json). These previously exposed suites establish regression results, not new blind accuracy or standalone TLS interpretation quality. Fixtures, expected evidence and scorers were not changed. |
| 16. Remaining limitations | Leaf inspection only; no OCSP/CRL, revocation result, certificate transparency, full chain export or cipher/security audit. Runtime validation stops at its first error, so failed trust does not isolate all chain problems. Separate handshakes may encounter different server chains; successful leaf identity must agree, while a failed validation handshake cannot supply a comparable peer. One permitted address per check; no all-address availability assertion. Native TLS buffering is library-managed before the application DER cap. Count retention is not time retention. System clock/runtime trust configuration affect results. No LAN, browser visual, Linux/Docker or standalone TLS model-quality acceptance. |
| 17. Recommended next read-only integration | Bounded, credential-free HTTP response-header inspection for configured services, reporting observed security/cache/proxy headers as separate cited facts without changing configuration or asserting security from headers alone. Reuse pinning, redirect and response bounds. |

The first socket-test attempt stalled in Windows sandbox socket initialization.
That attempt was stopped; the completed socket tests, acceptance and local model
regressions ran with execution access outside that sandbox. Project dependencies
were installed into the repository virtual environment. Temporary local servers,
keys, test roots and isolated inventories were removed by fixture/script cleanup.

There is no certificate management, ACME, issuance/renewal, certificate upload or
replacement, trust installation, shell execution, SSH, Docker control, proxy
configuration, service restart or autonomous remediation feature in this milestone.
