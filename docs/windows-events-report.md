# Windows Event Log milestone report

Acceptance date: 29 October 2026. This milestone extends the existing working repository; pre-existing HTTP/DNS/TLS and other uncommitted changes were preserved.

1. **Windows API/provider used.** A dedicated `NativeEvents` provider calls `wevtapi.dll` through standard-library `ctypes`. Only query, next-record, XML render, publisher metadata, message formatting and close APIs are bound. No new dependency or shell execution was added. See the [provider](../backend/app/services/windows_events.py) and [Microsoft API reference](https://learn.microsoft.com/en-us/windows/win32/api/winevt/index).

2. **Channels supported.** System, Application and Security. The channel command probes this supported inventory rather than enumerating all custom Windows channels. The current host reports System/Application readable and Security unavailable with permission denied. Other platforms return an unavailable state without failing startup. Intended environment: native Windows 10/11 or Windows Server 2016+, Python 3.12+; tested host reports NT 10.0 build 26200.

3. **Fields captured.** Channel, provider, event ID, native level and derived severity, UTC timestamp, original native timestamp, computer, record ID, task, opcode, keywords, exact rendered message/render status, structured EventData and source XML. Missing optional data remains unknown/null. Original XML retains native timestamp precision and fields not flattened into the schema.

4. **Filters and bounds.** Default latest 100 warning-or-higher System records; hard maximum 200. Exact provider/event ID/channel, native severity threshold, timezone-aware start/end, record ID, older-record pagination, and ±5 minute correlation queries (configurable up to ±60) are supported. Explicit windows are limited to seven days. Per-event XML/message buffers are 64 KiB, returned data one MiB, native reads have a five-second application deadline and two read slots. Selection is capped at 50 unique events/one MiB with a ten-second inter-read deadline. Native timestamps use UTC `Z` in XPath. No complete log is loaded into application memory.

5. **Permissions.** Reads use the existing process token. Access denied and unavailable channels are explicit supported results; no privileges, audit settings or ACLs are changed. `doctor` adds per-channel PASS/WARN results without requiring Security for readiness. The sandbox initially denied all channels; authorized execution outside that sandbox demonstrated normal System/Application access and continued Security denial. No UAC elevation or Windows privilege adjustment was used. The read-only Administrator-token check returned false for the acceptance process.

6. **CLI changes.** `grimoire events channels|recent|search|inspect|analyse`, bounded filter flags, `--json`, human-readable native facts, exact-channel inspection, optional native-model analysis and inventory-service correlation. Existing generic log commands retain their behaviour.

7. **API changes.** `GET /api/events/channels`, `GET /api/events`, `GET /api/events/{record_id}` and `POST /api/events/analyse`. Analysis accepts a bounded query or verified selections; optional `incident_title` uses existing local incident storage. `POST /api/incidents/summarise` also accepts `event_selection` alongside supplied logs. Invalid filters return 422, absent inspected records 404, changed/missing selected evidence 409, oversized selection 413. No host control endpoint was added.

8. **UI changes.** A focused Windows Events panel in Logs & incidents with channel, severity, exact provider, event ID, time-window and around-timestamp filters, older-page navigation, bounded selection, exact source details, local explanation, inventory-service correlation and incident creation. Verified in the browser against the real host: 100 System records, 10 warning-or-higher Application records in the selected 24-hour window, selected Application explanation with the native model, and incident creation. Security denial displays zero records and clears stale results. These counts describe that acceptance run, not ongoing host totals. [Permission-state screenshot](windows-events-evidence/ui-permissions.jpg) deliberately contains no event payloads.

9. **Evidence integration.** `windows_event` records have a source-XML SHA-256 `WE-` identity, full source fields and deterministic line references. Models cannot supply or edit event fields. Selected references are reread and hash-checked; duplicate selections cannot inflate counts. Chat exposes typed Windows live evidence. No automatic vector ingestion occurs.

10. **Log-analysis integration.** Windows observations adapt into the shared events/counts/pattern/time-range contract, reusing `model_events`, `explain_logs`, interpretation validation, citations, confidence and uncertainty, and the existing incident renderer/store. Exact channel/provider/event-ID grouping retains member timestamps and identities. Model interpretations remain limited to the existing validated symptom classes, with Unknown for unsupported causes. No fuzzy message-only merging or second analysis engine was introduced.

11. **Service/time correlation.** Operator-selected inventory services are compared with retained HTTP/DNS/TLS observations (up to 50 of each) within ±5 minutes. Source type, observation ID/time and matched event evidence IDs remain separate; timing never asserts host association or causation. Real acceptance measured a healthy test-owned loopback HTTP endpoint and found **9 existing System events** in the surrounding window, producing **one separate HTTP observation relationship**. No real service outage, service control or manufactured Windows event was used. Positive and excluded-time matches also have deterministic fixture coverage.

12. **Incident integration.** Selected native events can create an incident or join supplied logs and operator notes in the existing pipeline. Correlated HTTP/DNS/TLS observations are stored separately with deterministic IDs/timestamps. Mixed timelines order explicit-offset timestamps chronologically, preserve original line references and put unknown/naive times after known ones without guessing a timezone. Raw selected evidence is retained in Grimoire's own local incident data and exports.

13. **Real Windows acceptance.** PASS: supported channel inventory, System retrieval, Application retrieval, real error subsets, rendered messages, exact provider/event filters, native severity filtering, around-timestamp filtering, record identity, bounded pagination, CLI, API, UI, native-model explanation and incident creation. Each channel's initial sample contained five real records with five rendered messages; each also yielded three real error records. The final local model classified the selected System errors as a possible timeout symptom with validated L1/L2/L3 references. This is a symptom interpretation, not a root-cause finding. See [sanitized acceptance results](windows-events-evidence/acceptance.json) and the [reproducible script](../scripts/windows_events_acceptance.py).

14. **Privacy/security controls.** No write/control APIs, subscriptions, permission changes, shell, PowerShell or remediation. No raw event contents in application logs or acceptance reports. All Security payloads are excluded from model context. System/Application model input is limited to at most 12 whole event messages/5000 serialized characters plus bounded question/notes; XML and structured payloads stay outside model input. Every candidate/fallback must use in-process native inference; remote/unknown/Ollama adapters are refused for Windows evidence. No cloud transport is added. Host-event replies are excluded from frontend model conversation history. UI/docs explain usernames, hostnames, paths, IPs, SIDs and authentication metadata; selected local incidents/exports/backups contain sensitive data and are not additionally encrypted.

15. **Tests added and totals.** Added **33 backend Windows-event tests** and **2 frontend event tests**. Coverage includes all native severity levels, optional/malformed data, provider/channel distinction, repetition, denied/missing channels, non-Windows behaviour, query bounds/timestamps, evidence identity/selection, byte limits, deduplication, mixed timeline ordering, local-model restrictions, Security exclusion, rejected invented references, API, CLI, chat/streaming, correlation and incident assembly. Final results: **520 backend tests passed**, **10 frontend tests passed**; frontend syntax checks, backend Ruff checks and `git diff --check` passed. One existing Starlette/httpx test-client deprecation warning remains. Full backend execution includes HTTP monitoring, DNS, TLS, log/incident and deployment tests. [Backend result](windows-events-evidence/backend-tests.txt), [frontend result](windows-events-evidence/frontend-tests.txt).

16. **Reliability regression results.** Both suites ran with the existing local Qwen2.5 1.5B Q4_K_M generation model and MiniLM embedding model. Development: grounded QA 10/10, oracle QA 10/10, unsupported 4/4, oracle unsupported 4/4, logs/extraction/incidents 6/6 each, retrieval hit@5 10/10, 18/18 traceable validated claims, zero rejected outputs. Held-out: grounded/oracle QA 22/22 each, unsupported/oracle unsupported 5/5 each, logs/extraction/incidents 7/7 each, retrieval hit@5 22/22, 25/25 traceable validated claims, zero rejected outputs. Suite hashes match the previous TLS milestone. [Reliability summary](windows-events-evidence/reliability-summary.json), [full synthetic report](windows-events-evidence/reliability.json).

17. **Remaining limitations.** Three local channels only; no remote sessions, custom-channel UI, exported EVTX or Linux support. Native publisher resources can be missing; oversized events are explicitly omitted. Pagination can change under log rotation. Record IDs require a channel and selected hashes must still match. OS calls themselves are not forcibly preempted. Security could not be inspected on this host and is never sent to the model. Optional event AI currently requires native inference and uses the existing narrow symptom vocabulary. Chat intent/time parsing is deliberately limited; exact incident windows use explicit filters. There is no automatic mapping from Windows service identifiers to inventory services, no causal conclusion from time proximity, and no real failed-service acceptance scenario was induced. Only this Windows host was tested across the intended OS range.

18. **Recommended next host integration.** Read-only Windows service-status inventory using the Service Control Manager's query APIs (`QueryServiceStatusEx` and configuration reads). Explicit host/service identity mapping would make event-to-inventory association more reliable while keeping all start/stop/restart/configuration controls absent. This recommendation is not implemented in this milestone.
